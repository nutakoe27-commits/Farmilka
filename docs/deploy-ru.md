# Запуск генерации на арендованной GPU

Инструкция для закрытого пилота, бюджет **$50–150 в месяц**, доступ по SSH.
Платные ресурсы ещё не арендованы. Все команды выполняются из корня нового
проекта; прежний каталог `/workspace/Farmilka` не используется. GitHub-репозиторий —
`nutakoe27-commits/Farmilka`. В Git работаем только в `main`.

## 1. Что арендовать

Первый выбор для экономного теста — **Vast.ai**, один проверенный хост с RTX 3090
24 GB. Запасной вариант — **Runpod Pods**, RTX 3090 или RTX 4090 24 GB: удобнее
типовой запуск, но итоговая цена зависит от доступного предложения и диска.
Сравнивайте полную стоимость и доступность конкретных предложений при аренде.
Рекомендация Vast.ai основана на возможности выбирать предложения разных
хостов, а не на подтверждённой минимальной цене на сегодня.

| Параметр | Для первого запуска |
| --- | --- |
| GPU | 1 × RTX 3090 24 GB; RTX 4090 24 GB при близкой цене |
| RAM | 32 GB минимум для первого теста с offload; 48–64 GB предпочтительнее |
| CPU | 4 vCPU или больше |
| Постоянный диск | 100 GB; веса, кэш, окружение и результаты |
| Система | Linux x86_64, Python 3.12, NVIDIA driver 570+ для выбранного CUDA 12.8 стека |
| Режим аренды | On-demand для первого запуска; прерываемые экземпляры — после проверки восстановления |
| Сеть | Загрузка весов с Hugging Face, пакетов с PyPI/PyTorch; SSH |
| Предельная цена поиска | Начните с фильтра $0.25/GPU-час; это ваш потолок, не тариф провайдера |

Сверьте RAM, объём диска, пропускную способность и надёжность выбранного
хоста. Для первого теста выбирайте уже проверенный хост; при отсутствии
подходящего предложения сравните Runpod. Не выбирайте 8 GB только по
минимальному объёму из рекламы модели: воркеру нужны также текстовый энкодер,
VAE и память для конкретного разрешения. Реальное потребление предстоит измерить.

**Текущие тарифы не подтверждены:** страницы провайдеров вернули 403 от сетевого
прокси этой среды. Ссылки для проверки перед оплатой:

- Vast.ai: <https://vast.ai/pricing>
- Runpod: <https://www.runpod.io/pricing>
- Оплата Pods: <https://docs.runpod.io/pods/pricing>

## 2. Как уложиться в бюджет

Формула: `GPU-час × часы работы + диск + исходящий трафик + CPU-сервер`.

Примеры расчёта, **не коммерческие предложения**:

| Условная ставка | 100 часов | 300 часов | 730 часов, примерно месяц 24/7 |
| --- | ---: | ---: | ---: |
| $0.20/час | $20 | $60 | $146 |
| $0.25/час | $25 | $75 | $182.50 |
| $0.30/час | $30 | $90 | $219 |

Диск и остальные расходы добавляются отдельно. При бюджете $100, условных
прочих расходах $10 и ставке $0.25/час доступно `(100-10)/0.25 = 360` часов.
Потолок баланса и уведомления о расходах задайте в кабинете провайдера.
Начните с одного тестового часа и небольшого пополнения. Измерьте время
генерации 512/768/1024 и расход памяти, прежде чем считать себестоимость фото.

**Остановка Python, воркера или Docker не останавливает оплату GPU.** Для
остановки списаний используйте Stop/Terminate/Destroy в кабинете провайдера и
проверьте статус и биллинг. При Stop может продолжить оплачиваться диск.
Перед удалением экземпляра скачайте нужные результаты; проверьте отдельно,
какие тома сохраняются выбранным режимом аренды.

## 3. Выбранная модель

`black-forest-labs/FLUX.2-klein-4B`, distilled, четыре шага, `guidance_scale=1.0`.
Официальный репозиторий подтверждает text-to-image, single-reference editing,
multi-reference editing и Apache 2.0 для **4B**:

- <https://github.com/black-forest-labs/flux2>
- <https://huggingface.co/black-forest-labs/FLUX.2-klein-4B>
- <https://github.com/huggingface/diffusers/blob/main/src/diffusers/pipelines/flux2/pipeline_flux2_klein.py>

В текущем приложении один reference image. Версии 9B/dev имеют другую лицензию;
простая замена названия модели не является проверенной коммерческой конфигурацией.
Веса скачиваются непосредственно на ваш сервер, inference выполняется там же.
В приложении нет внешнего API генерации или добавленного фильтра промптов.
Способность выполнить любой запрос из этого не следует: результат зависит от
обучения модели. Специфические сценарии требуют отдельной оценки качества.

Первое скачивание фиксирует точный commit SHA в
`MODEL_DIR/download-manifest.json`. Последующие старты используют ту же ревизию.
Обновление выполняется явно через `--refresh`; `.bin`/pickle-веса и удалённый
Python-код модели не используются. Проверка TLS остаётся включённой.
Завершённое скачивание отмечается manifest: обычный перезапуск использует
локальные файлы. Для восстановления удалённых файлов повторите загрузку с
`--revision SHA_ИЗ_MANIFEST`.

## 4. Подготовьте архив проекта

На машине, где находится новый проект:

```bash
cd /workspace/new-project
git symbolic-ref --short HEAD
sh scripts/package.sh /tmp/photo-service.tar.gz
```

Первая команда Git должна показать `main`. Архив не включает `.git`, `.env`,
пользовательские фото, результаты, окружение и модели. Учётные данные в архив
не попадают. Хост, пользователя и SSH-порт возьмите из кабинета аренды.

```bash
scp -P SSH_PORT /tmp/photo-service.tar.gz USER@GPU_HOST:/tmp/photo-service.tar.gz
ssh -p SSH_PORT USER@GPU_HOST
mkdir -p /workspace/photo-service
cd /workspace/photo-service
tar -xzf /tmp/photo-service.tar.gz
```

`USER`, `GPU_HOST`, `SSH_PORT` замените вашими значениями. Если `/workspace`
отсутствует на обычной VM, создайте каталог с правами своего пользователя или
используйте свой рабочий каталог и настройте пути к кэшу в bootstrap.

## 5. Выберите способ запуска

**Runpod Pod или контейнерный экземпляр Vast.ai:** вы уже внутри контейнера.
Используйте вариант A с Python. Доступ к Docker host в таких окружениях обычно
не предоставляется; выполнение `docker compose` внутри Pod не предполагается.

**Полноценная GPU VM с Docker и NVIDIA Container Toolkit:** используйте вариант B.
В обоих случаях нужен доступ к GPU через `nvidia-smi`. При выборе шаблона
предпочтите актуальный официальный PyTorch/CUDA-шаблон провайдера с Python 3.12.
Системные версии PyTorch внутри шаблона не заменяют зависимости нашего `.venv`.

### Вариант A: Python внутри арендованного контейнера

Подключитесь по SSH и выполните:

```bash
cd /workspace/photo-service
nvidia-smi
python3 --version
sh scripts/bootstrap.sh --gpu
.venv/bin/python scripts/gpu_probe.py
```

Bootstrap использует `uv`, создаёт отдельное окружение из `uv.lock` и приватный
`.env` с двумя случайными ключами. При отсутствии `uv` он устанавливает его в
`/workspace/photo-bootstrap`. При отсутствии Python 3.12 uv может скачать
собственный runtime. Не редактируйте lockfile ради успешной установки.

Откройте `.env` редактором на сервере. Сохраните уже созданные ключи и задайте:

```dotenv
ENGINE=flux
CONTROL_URL=http://127.0.0.1:8000
MODEL_DIR=/workspace/photo-service/models/flux2-klein-4b
MODEL_CPU_OFFLOAD=true
DATA_DIR=/workspace/photo-service/data
```

Каталог проекта, `data`, `models` и кэш должны лежать на постоянном диске Pod.
Наличие такого диска и его сохранение при Stop проверяются в настройках аренды.
Ключи из `.env` не отправляйте в чат, Git или общие журналы.

Загрузите веса. Первое скачивание занимает время и дисковое место:

```bash
set -a
. ./.env
set +a
.venv/bin/python -m photo_service.download_model
```

Стандартная публичная модель должна проверяться без запроса нового токена.
Если Hugging Face вернёт 401/403, сначала проверьте карточку модели, наличие
заданного `HF_TOKEN`, доступ аккаунта и сетевую ошибку. Только при реальной
необходимости создайте read-only токен в Hugging Face и задайте его через
секреты провайдера. Не вставляйте значение в командную строку или репозиторий.

Запустите API и воркер в отдельных SSH-терминалах или сессиях `tmux`:

```bash
cd /workspace/photo-service
.venv/bin/uvicorn photo_service.api:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log
```

Во втором терминале:

```bash
cd /workspace/photo-service
.venv/bin/python -m photo_service.worker
```

После `Engine ready: flux` проверьте из третьего терминала:

```bash
cd /workspace/photo-service
.venv/bin/python scripts/smoke.py --expect-engine flux --output /tmp/first-photo.png
.venv/bin/python scripts/smoke.py --expect-engine flux --reference /tmp/first-photo.png --output /tmp/edited-photo.png
```

Ожидается `PASS engine=flux`, PNG 512×512 и фактический результат в указанных
файлах. Второй запрос проверяет передачу reference image, но не оценивает
качество редактирования. Посмотрите обе картинки. Повторите запросы с вашими
обычными промптами на русском и английском и сравните качество. Остальные
языки проверяйте отдельно: перевод интерфейса не является тестом модели.

Для сохранения процессов после отключения SSH используйте `tmux`:

```bash
tmux new -s photo
```

Запустите API в первом окне, создайте второе через `Ctrl+B`, затем `C`, запустите
воркер. Отсоединиться: `Ctrl+B`, затем `D`. Вернуться: `tmux attach -t photo`.
После перезапуска Pod процессы запускаются заново; файлы на постоянном томе
сохраняются. `tmux` не обеспечивает автоматический запуск после reboot.

### Вариант B: GPU VM с Docker

На VM должны работать Docker Compose 2.30+ и NVIDIA Container Toolkit.
Установку Toolkit выполняйте по официальной инструкции для вашей ОС:
<https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html>.
Не применяйте команды для хостового драйвера внутри арендованного Pod.

```bash
cd /workspace/photo-service
nvidia-smi
docker compose version
python3 scripts/init_env.py
docker compose --profile gpu config --quiet
docker compose --profile gpu build
docker compose --profile gpu run --rm --no-deps gpu-worker python scripts/gpu_probe.py
docker compose --profile gpu up -d
docker compose logs --tail 100 -f api gpu-worker
```

Проверка `gpu_probe.py` требует файл `scripts/gpu_probe.py` внутри GPU-образа;
он включён в Dockerfile. Сборка GPU-образа скачивает крупные CUDA-зависимости.
Первый старт воркера дополнительно загружает модель в том `photo-models`.
Готовность API и готовность модели — разные состояния. Дождитесь
`Engine ready: flux`, затем запустите функциональные проверки:

```bash
docker compose exec -T api python scripts/smoke.py --expect-engine flux --output /tmp/first-photo.png
docker compose cp api:/tmp/first-photo.png /tmp/first-photo.png
```

Остановка процессов без удаления данных:

```bash
docker compose --profile gpu down
```

Не добавляйте `-v`, если хотите сохранить фото, SQLite и веса. Это команда
остановки приложения, а не остановки оплаты аренды.

Если сборка выполняется в облачной среде Codex с её прокси, используйте
`DOCKER_CONFIG=/workspace/.cache/docker python scripts/build_image.py`
(для GPU добавьте `--gpu`), затем `docker compose --profile gpu up -d --no-build`.
Этот helper передаёт существующие настройки прокси и CA в builder, сохраняя
проверку сертификатов. На обычной VM без такого прокси достаточно команд выше.

## 6. Откройте интерфейс через SSH-туннель

На своём компьютере, в отдельном терминале:

```bash
ssh -p SSH_PORT -N -L 18000:127.0.0.1:8000 USER@GPU_HOST
```

В браузере компьютера откройте loopback-адрес с портом `18000`.
Это личный SSH-туннель, не публичная ссылка или облачное превью.
Ключ `API_TOKEN` возьмите из `.env` через приватный редактор и введите в поле
доступа. Он хранится в памяти вкладки. `WORKER_TOKEN` в браузер не вводится.
Введите промпт, выберите размер, при желании загрузите фото, нажмите создание.
При выключенном воркере задание останется в очереди.

## 7. Перезапуск и диагностика

| Симптом | Что проверить |
| --- | --- |
| `worker_online=false` | Процесс воркера, завершение загрузки модели, `CONTROL_URL`, совпадение `WORKER_TOKEN` |
| `CUDA unavailable` | `nvidia-smi` на хосте и внутри контейнера, GPU passthrough и драйвер |
| `out_of_memory` | Сначала 512×512, один воркер, `MODEL_CPU_OFFLOAD=true`, другие GPU-процессы |
| Процесс убит без Python traceback | RAM хоста и ограничения контейнера; 48–64 GB предпочтительнее |
| HF 403 или ошибка CONNECT | Домен, сетевой доступ или разрешение модели; не отключайте TLS |
| `401` от API | Ключ пользователя для `/api`, ключ воркера для `/internal` |
| Долго `queued` | Worker ещё не готов, остановлен или обрабатывает предыдущее задание |
| `worker_lost` | Три истёкшие попытки аренды задания; восстановите воркер и отправьте новое |
| Пропали файлы после удаления Pod | Использовался временный диск или удалён постоянный том |

После рестарта API SQLite сохраняет задания. Каждое задание арендуется на 180
секунд; воркер продлевает аренду каждые 20 секунд. Просроченное задание может
быть выдано снова; после трёх попыток становится failed. Доставка результата
после потери аренды отвергается. При обрыве сети возможна повторная GPU-работа;
очередь не обещает строго однократное выполнение.

Не запускайте demo-worker и gpu-worker одновременно для одной очереди:
любой из них сможет забрать очередное задание. Переключение с демонстрации:

```bash
docker compose --profile demo stop demo-worker
docker compose --profile gpu up -d api gpu-worker
```

## 8. Данные и резервное копирование

Фото хранятся до удаления оператором: автоматического срока хранения пока нет.
В закрытом пилоте пользователь с общим API-ключом имеет общий доступ к заданиям.
Перед публичным запуском нужны аккаунты и проверка владельца каждого файла.

Для согласованной копии остановите API и воркер, затем скопируйте **весь** `data`
(SQLite, возможные WAL/SHM, inputs, outputs), снова запустите процессы. Для
Docker используйте резервное копирование тома `photo-data` после остановки
контейнеров. `.env` храните отдельно в защищённом месте. Веса можно повторно
скачать по SHA из manifest; их резервная копия экономит время и трафик.

## 9. Когда появятся первые пользователи

Сначала вынесите API на постоянный CPU-сервер, а GPU-воркер подключите к нему
через `CONTROL_URL=https://ваш-домен` и отдельный `WORKER_TOKEN`. Для этого уже
есть протокол выдачи заданий; публичного входящего порта на GPU не нужно.
CPU-сервер и домен оплачиваются отдельно и сейчас не созданы.

Следующий этап приложения: индивидуальная авторизация, владение заданиями,
лимиты и кредиты, оплата, автоматическое удаление файлов, HTTPS, мониторинг,
автоматический запуск/остановка GPU и замер задержек по регионам. Глобальная
доступность также зависит от провайдера, платежей и сети, а не только от перевода.
Это отдельная работа перед публичной продажей доступа. Сейчас подготовлен
путь к проверяемому закрытому GPU-пилоту.
